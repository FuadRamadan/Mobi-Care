Prompt: Patient Portal — Forgot Password via Email OTP

Add a self-service password reset flow to the Patient PWA, triggered when a patient forgets their password. Unlike the pharmacy flow (which routes through HQ), patients should be able to reset independently via a one-time code sent to their registered email.

1. Flow
Patient clicks "Forgot Password" on the login screen.
Patient enters the email address associated with their account.
System verifies the email exists in the database (see security note below on response wording), generates a 6-digit numeric OTP, and emails it from mobicaresl00@gmail.com.
Patient enters the OTP on the next screen.
On valid OTP, patient is taken to a "Set New Password" screen (subject to the same password policy/complexity rules used elsewhere in the system).
On successful reset, all existing sessions for that account are invalidated, and the patient is redirected to login with the new password.
2. Backend Endpoints
POST /api/patient/auth/forgot-password
Input: email. Generates OTP, stores hashed OTP + expiry, sends email via configured SMTP/mail service using mobicaresl00@gmail.com as sender. Always returns a generic success response regardless of whether the email exists (prevents account enumeration — see security notes).
POST /api/patient/auth/verify-otp
Input: email, otp. Validates OTP against stored hash and expiry. On success, issues a short-lived "reset token" scoped only to the password-change endpoint.
POST /api/patient/auth/reset-password
Input: reset token, new_password. Validates against password policy, updates password_hash, invalidates the reset token and all active sessions.
3. Data Model
patient_accounts
- otp_hash              TEXT NULL
- otp_expires_at         TIMESTAMP NULL
- otp_attempts           INTEGER DEFAULT 0
- otp_last_sent_at       TIMESTAMP NULL
4. Security Requirements
OTP expiry: 5–10 minutes is typical; make it configurable.
Hash the OTP before storing — never store it in plaintext, same standard as passwords.
Rate limiting: limit OTP requests per email/IP (e.g., max 3 per 15 minutes) to prevent abuse and email flooding.
Attempt limiting: lock out OTP verification after 5 failed attempts, requiring a fresh OTP request.
Account enumeration protection: the forgot-password endpoint should return the same generic message ("If an account exists with this email, a code has been sent") whether or not the email is registered — never confirm/deny existence directly.
Single-use OTP: invalidate the OTP immediately after successful verification.
Session invalidation: on successful password reset, log the account out of all devices/sessions.
5. Email Requirements
Sender: mobicaresl00@gmail.com
Subject line: something clear and branded, e.g., "Your MobiCare Password Reset Code"
Body: OTP code, expiry time, and a note like "If you didn't request this, you can safely ignore this email."
Use the existing notification/email service in the codebase if one exists (check for a mailer utility already used for other patient notifications) rather than building a new SMTP integration from scratch.
6. Frontend Screens
Forgot Password (email entry)
Enter OTP (with resend option, disabled/cooldown after use until rate limit window passes)
Set New Password (with live complexity validation, matching the pattern used elsewhere in the app)
7. Acceptance Criteria
 Patient can request a reset code by entering their registered email.
 OTP is emailed from mobicaresl00@gmail.com and expires after the configured window.
 Invalid/expired/reused OTPs are rejected with clear error messaging.
 Successful reset invalidates all existing sessions.
 System never reveals whether a given email is registered.
 Rate limiting prevents OTP request spam.
