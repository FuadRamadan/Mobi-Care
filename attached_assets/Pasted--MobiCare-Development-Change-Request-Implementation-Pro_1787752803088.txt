# MobiCare Development Change Request — Implementation Prompt

## Role

Act as a **senior full-stack software engineer, solution architect, database engineer, QA engineer, and security specialist** responsible for implementing the approved changes to the MobiCare platform.

The affected modules are:

* Pharmacy Portal
* Patient App
* HQ Portal
* Orders & Delivery
* Settlements
* Notifications
* Financial Reporting

Your implementation must be production-ready, secure, maintainable, and fully integrated with the existing MobiCare architecture.

---

## 1. Critical Priority — Fix Existing Data Integrity Bug First

Before implementing any new feature, investigate and resolve the existing **courier delivery-count bug**.

Currently, deliveries completed by couriers are not correctly reflected in the HQ dashboard. This may also affect:

* Delivery statistics
* Delivery settlement calculations
* Delivery commission
* Financial dashboards
* Revenue and payout totals
* Any reports derived from delivery counts

Trace the complete data flow from:

**Courier completes delivery → Order status → Delivery record → Settlement calculation → HQ dashboard/reporting**

Identify the root cause rather than applying a superficial UI fix.

After fixing the issue:

1. Verify that completed deliveries are correctly recorded.
2. Verify that HQ dashboard counts update correctly.
3. Verify that settlement calculations use the correct delivery data.
4. Verify that historical records are not corrupted.
5. Add appropriate automated tests to prevent regression.

**Do not proceed to feature implementation until this bug has been investigated and the fix has been validated.**

This requirement is explicitly identified as the highest-priority issue in the change request.

# 2. Pharmacy Portal

## 2.1 Order Status Workflow

Replace the existing order-status workflow with exactly three primary stages:

**Confirmed → Packaged → Collected**

Requirements:

* Each status must be completed as a single action from the order details/view.
* The user must not need to navigate to another page.
* "Collected" means the order has been collected by the **courier**, not the patient.
* Preserve appropriate timestamps and audit information for each status transition.

Do not introduce additional status stages unless they already exist as necessary technical/system states.

---

## 2.2 Automatic 5% Markup

Pharmacies enter their own selling price for each medicine.

The system must automatically calculate the patient-facing price using a configurable markup.

Formula:

**Patient Medicine Price = Pharmacy Entered Price × 1.05**

Therefore:

**MobiCare Medicine Revenue = Pharmacy Entered Price × 0.05**

**Amount Owed to Pharmacy = Pharmacy Entered Price**

The markup percentage must be stored as a **configurable system value** and must not be hardcoded.

For every transaction, store the actual markup rate used at the time of the transaction so that historical transactions remain accurate if the configured rate changes later.

### Important calculation rule

The 5% markup is calculated **on the pharmacy's entered price**, not on the final patient-facing price.

Do not incorrectly calculate the commission as 5% of the final patient price.

The implementation must preserve this distinction throughout:

* Database calculations
* Backend APIs
* Checkout
* Orders
* Settlements
* Reports
* Dashboards

---

## 2.3 Hide MobiCare Commission From Pharmacies

The pharmacy portal must not expose MobiCare's commission or markup.

Pharmacies should only see:

* Their own entered selling price
* Their own earnings
* Relevant order information

Do not display:

* MobiCare markup
* Commission percentage
* Commission amount
* Patient-facing price
* Commission line items

Ensure this restriction is enforced at both the **UI and API/data-access level**, not only by hiding fields in the frontend.

---

## 2.4 Pharmacy Daily Revenue

Add a **Daily Revenue** figure to the pharmacy dashboard.

The value must represent:

**Sum of the pharmacy's own entered prices for completed orders during the current day.**

No deductions should be displayed because the pharmacy receives exactly the amount it entered.

The calculation must use the pharmacy's original transaction price rather than the patient-facing price.

---

## 2.5 Automatically Populate Approved Prescriptions

When a pharmacist approves a prescription:

1. Retrieve the medicines originally requested by the patient.
2. Automatically populate those medicines into the pharmacy order.
3. Display the populated medicine list to the pharmacist.
4. Allow the pharmacist to edit the list where appropriate.
5. Do not require the pharmacist to manually re-enter the patient's requested medicines.

Ensure that the implementation minimizes dispensing errors and maintains an audit trail where appropriate.

---

## 2.6 Default Order Sorting

The pharmacy order list must default to:

**Most recent orders first**

Sort by the time the order was received in **descending order**.

# 3. Patient App

## 3.1 Confirm Delivery

Add a **Confirm Delivery** button to the patient's order-tracking page.

The patient can use this action to confirm that their medication has been received.

The system must:

* Update the appropriate delivery status.
* Record the confirmation timestamp.
* Record that the delivery was confirmed by the patient.
* Prevent inappropriate duplicate confirmations.

---

## 3.2 HQ Delivery Confirmation Fallback

HQ must be able to manually mark an order as delivered if the patient does not confirm delivery.

For every completed delivery, record:

* Confirmation method: **Patient** or **HQ**
* Confirmation timestamp
* If confirmed by HQ:

  * HQ user who performed the action
  * Date/time of confirmation

This ensures that orders do not remain indefinitely pending because a patient failed to confirm delivery.

---

## 3.3 Patient Age Requirement

Patient age must be required for every delivery order.

An order must not be submitted without the required age information.

However, **do not make assumptions about the final implementation of the age field.**

The Product Owner must confirm whether the system should capture:

* Date of birth, or
* Age

The Product Owner must also confirm whether age should:

* Simply be recorded, or
* Be used to prevent certain orders.

Until this is confirmed, do not implement additional age-based restrictions.

---

## 3.4 Patient Profile

Add a patient profile section containing:

* Address — Optional
* Email — Optional

National ID/NIN must **not** be collected from every user by default.

NIN upload should only be required where necessary for controlled-substance collection.

Any stored identity documents must:

* Be encrypted at rest.
* Have access restricted to authorized roles.
* Not be exposed through unauthorized APIs.
* Follow appropriate security and access-control practices.

---

# 4. HQ Portal

## 4.1 Move Financial Dashboard to Settlements

Move the financial dashboard into the **Settlements** section.

All other HQ dashboards should remain in the general HQ dashboard area and should not be unnecessarily changed.

The Settlements section must have stronger access control.

Implement either:

* Separate authentication, or
* An elevated permission/role

Only authorized users should be able to view financial information.

Ensure authorization is enforced server-side and not only through frontend navigation restrictions.

---

# 5. Settlements Dashboard

Create a dedicated Settlements dashboard containing:

### Daily Commission Income

Show:

**Medicine Markup Revenue + Delivery Commission**

### Total Owed to Pharmacies Today

Calculate the total amount payable to pharmacies based on their actual entered prices for completed qualifying orders.

### Total Owed to Delivery Partner Today

Calculate the amount owed to the delivery partner using the existing approved delivery commission logic.

### Cumulative Revenue

Allow authorized users to select a date range and view cumulative revenue for that period.

### Pharmacy Breakdown

Provide a breakdown of:

* Revenue by pharmacy
* Pharmacy payouts
* Relevant transaction/order counts

All settlement calculations must use reliable transaction-level data and should be traceable back to the underlying orders.

Implement appropriate validation for uploaded images and secure storage/access.
